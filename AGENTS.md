# GiottoClass

The foundational S4 object framework for the [Giotto Suite](https://drieslab.github.io/GiottoClass/)
of spatial omics analysis tools. Defines the `giotto` object and all its
subobjects, data access methods, the spatial manipulation verbs, and the
generics that analysis packages attach methods to. Every other suite package
(Giotto, GiottoVisuals, GiottoDisk) builds on the classes defined here.

- **Package version:** 0.7.2
- **R requirement:** >= 4.5.0
- **Primary spatial backend:** `terra` (SpatVector / SpatRaster)

## Class Hierarchy

Two tiers: the `giotto` container (24 slots, mostly `nullOrList`) holds nested
lists of subobjects. Subobjects are self-describing — they carry their own
schema tags and are the unit that spatial verbs dispatch on.

Subobjects inherit from **two independent families of virtual class** at once:

```
# schema tags carried
provData        @provenance
featData        @feat_type
spatData        @spat_unit                    (contains provData)
spatFeatData    both axes                     (contains spatData, featData, provData)
nameData        @name

# how the payload is stored
gdtData         data.table-backed; [ $ nrow colnames behave like data.table
├── coordDataDT → spatLocsObj
└── metaData    → cellMetaObj, featMetaObj
exprData        → exprObj                      (matrix, Matrix, or a dataStore handle)
terraVectData   → giottoPolygon, giottoPoints  (external pointer)

# domain-specific
enrData → spatEnrObj    nnData → nnNetObj    spatNetData → spatialNetworkObj
spatGridData → spatialGridObj                miscData → has @misc
```

So `spatEnrObj` is `nameData` + `enrData` + `spatFeatData` + `gdtData`, and each
contributes a different set of inherited methods. **When adding a subobject,
pick one virtual from each of the first two families**, then a domain virtual
only if there is domain-specific behaviour to hang on it. Rationale and the
alternatives considered: `design.Rmd`, *Subobject class hierarchy*.

`giotto` slot lists nest to exactly the depth of the keys they need — no
placeholder levels:

```r
gobject@expression$cell$rna$raw     # spat_unit / feat_type / name
gobject@spatial_locs$cell$raw       # spat_unit / name
gobject@cell_metadata$cell$rna      # spat_unit / feat_type
```

## Key constraints

### `initialize()` runs on every set

The `giotto` `initialize()` method updates subobjects for class changes, ensures
instructions, validates active `spat_unit`/`feat_type`, derives `@cell_ID` /
`@feat_ID`, and runs hierarchical consistency checks. It is on the hot path of
every setter. Loops that set many objects should pass `initialize = FALSE` where
a setter exposes it and re-initialize once at the end.

ID derivation prefers `@expression` over `@spatial_info`/`@feat_info`. That
ordering is what lets an object be built in either order.

### `@source` is `NULL` or a backend manager

`is.null(gobject@source)` is the **one** test for "is this object backed"
(ADR 0001). There is no null-object standing in for in-memory, so every
write-through site guards explicitly.

On a backed object, `set*()` writes the payload to the vault via
`GiottoDisk::sourceWrite()` and stores the resulting `dataStore` in the slot
(ADR 0002). Two consequences for any code you write:

- Setters perform I/O. They can be slow and they can fail.
- **A slot may hold a store rather than a matrix.** Anything reaching for
  `dim()`, `is.matrix()`, or row/column names on slot contents needs a store
  branch. Validators (`.evaluate_*()`) pass store classes through unchanged —
  a validator must never materialize its input.

`@h5_file` is deprecated, kept in the class definition for one release so older
serialized objects load. Do not build on it; do not remove it yet.

### terra pointers do not serialize

`giottoPolygon` / `giottoPoints` hold a `SpatVector` — an external pointer to
C++ memory. It does not survive `saveRDS()` or a trip to a parallel worker, and
**it fails silently**: the object comes back empty rather than erroring.

**Use `saveGiotto()` / `loadGiotto()`** — serialization by reference. Each
`SpatVector` is written as its own shapefile (`.save_external()`, plus a
`_names.txt` sidecar since shapefiles truncate column names); the gobject is
`saveRDS`'d separately with dead pointers, and `.load_external()` re-reads the
shapefiles on load. Peak memory stays at one layer and the artifacts are
independently readable.

**`wrap()` / `vect()` and the `packed*` classes are unmaintained and may be
removed — do not build on them** (ADR 0005). Serialization by value copies every
layer into the R heap, which does not hold at project scale. They remain only
because `{GiottoData}`'s `giottoPoints` / `giottoPolygon` minis and older user
`.RDS` files are stored as `packedGiotto*` and still have to read back. There is
no runtime deprecation warning: the read direction is exactly the path that
legitimately still runs, and `deprecate_soft()` could not separate it from a
direct user call.

A new class wrapping a terra object gets `.save_external()` /
`.load_external()` methods and **no** `packed*` variant. `reconnect()` is the
raster equivalent — `SpatRaster` holds a file handle, written via
`writeRaster()` and re-opened from the recorded path.

### Networks store a graph in `@network`

Both `spatialNetworkObj` and `nnNetObj` store an `igraph` (or a GiottoDisk
`dataStore`) in a slot named `network` (ADR 0004). Construction goes through
`createNetwork(x, param)`; the four legacy constructors are wrappers.

Known gap: accessors that reach into `@network` assuming `igraph` — `spatIDs()`
on network objects among them — still need a `dataStore` branch.

### Object versioning

`@versions` records the producing GiottoClass version; `updateGiottoObject()` is
a linear sequence of version-gated migrations. Removed slots stay reachable via
`attr(gobject, "old_slot")` because S4 deserialization keeps the stored
representation — that is the mechanism for retiring a slot without breaking old
files (`.update_network_slots()` is the worked example).

When you change a class definition, add the migration in the same commit.

## Adding to the package

### A new generic

Almost always the wrong move. **Five analysis generics exist and are split by
return contract** (ADR 0003), and they are distinct, not synonyms:

| generic | returns |
|---|---|
| `processData()` | same-shape transform |
| `filterData()` | a selection (IDs to keep) |
| `reduceData()` | a decomposition / embedding |
| `clusterData()` | cluster assignments (`param` takes `bluster::BlusterParam`) |
| `analyzeData()` | computed outputs and summary statistics |

A new algorithm is a **new `Param` subclass plus a method in Giotto or
GiottoDisk** — not a new generic here. Route to the generic whose return
contract matches, or fall through to the `ANY,ANY` catch-all. A method attached
to the wrong generic silently never dispatches.

GiottoClass defines these generics and the virtual `Param` classes and exports
**no methods** for them.

If a generic genuinely is new, it goes in `R/generics.R` with an `@rdname` tag
and no implementation.

### A new class

1. `setClass()` in the appropriate `R/classes-*.R` file.
2. Export via `@exportClass`.
3. Constructor (e.g. `createGiottoFoo()`) in `R/create.R`.
4. Generics to `R/generics.R`; methods to `R/methods-<topic>.R`.
5. If it goes in a `giotto` slot, update the slot type union in `R/classes.R`
   and `R/zzz.R`.
6. `packed*` variant if it wraps a terra object.
7. Tests in `tests/testthat/`.

### A new method

Implementation goes in `R/methods-<topic>.R`, never next to the generic. A
generic defined next to one of its methods reads as belonging to that method,
and the next person adds a second generic instead of a second method.

### Dispatch outside S4

`R/flex_functions.R` holds `*_flex` helpers (`mean_flex`, `colSums_flex`, …).
They route to a method that is *not* the one defined for a class in its native
package — usually to stop sparse `Matrix` operations from densifying — without
polluting the user's environment with S4 dispatch they did not ask for. **Use
the flex function as a drop-in replacement inside suite code**, and prefer
adding one over a bare `setMethod` on a base generic for a class this package
does not own.

## Coding Conventions

Full style guide: https://giottosuite.com/articles/coding_style.html
Dispatch functions: https://giottosuite.com/articles/dispatch_functions.html

### Naming

| Type | Convention | Example |
|------|-----------|---------|
| Exported user-facing functions | `camelCase` | `createGiottoObject()` |
| S4 classes | `camelCase` | `giottoLargeImage` |
| Exported utility / non-user-facing | `snake_case` | `dt_to_matrix()` |
| Internal functions | `.snake_case` (leading dot) | `.detect_in_dir()` |
| Parameters / arguments | `snake_case` | `spat_unit`, `feat_type` |

Do not use periods as name separators — this conflicts with S3 dispatch.
Do not use non-UTF-8 characters; use Unicode escapes instead (e.g. `\u00F6`).

### Other

- **Style:** 4-space indentation, BioConductor conventions (`biocthis` +
  `styler`). Enforced by `lintr` in CI.
- **Imports:** all `@importFrom` declarations go in `R/package_imports.R`, not
  scattered across files.
- **Error handling:** bare `stop(..., call. = FALSE)` with a `[site]` prefix
  naming where the failure came from, e.g.
  `stop("[setGiotto] this space has no name", call. = FALSE)`. Not `gstop()` —
  it prepends the calling function automatically, which duplicates the prefix
  and reads worse from a deep internal frame. `gwarn()` / `gmessage()` are
  still the right thing for warnings and messages.
- **Validation:** `checkmate` at function boundaries.
- **Data tables:** prefer `data.table` idioms over base R for tabular work.
- **Never edit `NAMESPACE` or `man/` directly.** Run `devtools::document()`
  after changing any `@export`, `@importFrom`, or `@param` tag.

### Testing

```r
devtools::test()
testthat::test_file("tests/testthat/test_03_accessors.R")
```

Test data comes from the `GiottoData` package via `GiottoData::loadGiottoMini()`
and `GiottoData::loadSubObjectMini()`. Global setup is `tests/testthat/setup.R`:

```r
options("giotto.use_conda" = FALSE)      # No conda during tests
options("giotto.no_python_warn" = TRUE)  # Suppress Python warnings
options("lifecycle_verbosity" = "quiet")
```

Numbered tests (`test_01_*.R` … `test_10_*.R`) run foundational object creation
in order; the rest are named by functional area.

## Interoperability

Conversions live in `R/interoperability.R`. All are lossy — the schema above has
no counterpart in most of these formats, so a round trip does not preserve
provenance or multi-unit nesting.

| From / To | Function |
|-----------|----------|
| Seurat v4/v5 → Giotto | `seuratToGiotto()`, `seuratToGiottoV4()`, `seuratToGiottoV5()` |
| Giotto → Seurat | `giottoToSeurat()`, `giottoToSeuratV5()` |
| AnnData → Giotto | `anndataToGiotto()` |
| Giotto → AnnData | `giottoToAnnData()` |
| SpatialExperiment ↔ Giotto | `spatialExperimentToGiotto()`, `giottoToSpatialExperiment()` |
| SpatialData → Giotto | `spatialdataToGiotto()` |
